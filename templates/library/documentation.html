Development of Problem Statements

A Library Management System (LMS) is a project that manages and stores book information electronically according to user needs. The system helps students, faculty and the librarian to keep a constant track of all the books available in the library. It allows both the admin and the member to search for the desired book. It becomes necessary for educational institutes like colleges to keep a continuous check on the books issued and returned and even calculate fines.

Existing System: The existing system is physical maintenance of the library in which all transactions are done manually. This method takes more time for borrowing or returning a book and for searching members and books. Preparing lists of borrowed books and available books takes more time. It takes several days to verify all records in larger libraries.

Proposed System: The proposed system is a Book Bank / Library Management System. All difficulties in manual management have been rectified by implementing a computerized system. The administrator (librarian) can add members, add books, search members, search books, update information, edit information, borrow and return books quickly. The proposed system provides better and efficient service to members, reduces workload, allows faster retrieval of information, provides proper monitoring, reduces paperwork, provides data security, and makes all details available with a single click.

Preparation of Software Requirement Specification Document, Design Documents and Testing Phase Documents

Software Requirements Specification (SRS):

1. Introduction

1.1 Purpose: The purpose of this document is to record the requirements of an application that will automate the whole procedure of a library. This document reflects the features expecting from the software and constraints imposed on the development of the system.

1.2 Scope: The system LMS is a web-based application. For Members: facility for search of books based on Title, Author, Subject, Keyword; facility for ISSUE/RETURN books; facility for RENEWAL of books. For Library Staff: automatic installation; simple and intuitive GUI for performing all functions; shortcut keys and point-and-click operation; security features like access control using passwords and login-id; automatic calculation of late-fee; facility to ADD/DELETE Members, Library Staff and Books and maintain an easy record of all these.

1.3 Definitions, Acronyms and Abbreviations: LMS - Library Management System; GUI - Graphical User Interface; DBMS - Database Management System.

1.4 References: IEEE/ANSI 830-1998 SRD Standard.

1.5 Overview: The rest of the document deals with all the main features of this software. It not only describes various functions but also gives details about how these functions are related to each other.

2. Project Description

2.1 Product Perspective: The manual library management system includes drawbacks such as: a lot of paperwork and manual calculation leading to inconsistency and inaccuracy; data stored on paper may be lost, stolen or destroyed; existing system is sluggish and time-consuming; difficult to find or edit data of a specific book. The proposed LMS rectifies these by computerizing the library system, reducing paperwork, enabling easy book search, performing automatic fine calculations, and providing user-ID validation to prevent unauthorized access.

2.2 Product Functions: There are two users: Librarian (administrator) and Member. Librarian features: issue a book to member; view different categories of books; view list of books in each category; add books and their information to the database; edit information of existing books; check report of issued books; access all accounts of students. Member features: view different categories of books; view list of books in each category; search for a particular book.

2.3 User Characteristics: Staff needs complete understanding of functionalities and internal processing of the library system. Members are library users and need not have complete understanding of complex functionalities and internal processing.

2.4 General Constraints: The Online Library System is running 24 hours a day. Users may access LMS from any computer that has Internet browsing capabilities and an Internet connection. Users must have correct usernames and passwords to enter into their online accounts and do actions. The information of all users, books and libraries must be stored in a database accessible by the website.

2.5 Assumptions and Dependencies: Assumptions: coding should be error free; system should be user-friendly; information of all users, books and libraries must be stored in a database; system should have more storage capacity and provide fast access to the database. Dependencies: project will be developed on the basis of listing requirements and specifications; end users should have proper understanding of the product; information of all users must be stored in a database accessible by the LMS.

3. Specific Requirements

3.1 Functional Requirements: A functional requirement is a statement of how a system must behave. It defines what the system should do to meet user needs. Functional requirements of Book Bank/Library System: (1) Add, remove and manage books from the library; (2) Search for books by title, author, or ISBN; (3) Issue and return books; (4) Display a list of all books; (5) Store and retrieve information about library staff; (6) Generate reports on library usage and checkouts; (7) Allow librarian to add and remove new members; (8) Users can request, reserve, or renew a book; (9) Track which books are currently checked out and when due; (10) Calculate fine for overdue books on return.

3.2 Non-Functional Requirements: Non-functional requirements explain limitations and constraints. They define how the system should work internally.

3.2.1 Product Requirements: Usability - staff shall be able to use all features with 2 hours of training; Performance - home page shall support 100 users per day with 10 seconds or less response time over 1Mbps connection; Reliability - system must perform without failure in 95 percent of uses during a month; Portability - system running on Windows 10 must run on Windows 11 without change; Scalability - must support 2000 visits at the same time; Availability - must be available 95 percent of the time every month during college hours; Maintainability - mean time to restore (MTTRS) following failure must not be greater than 45 minutes.

3.2.2 Organizational Requirements: Delivery - system should be delivered as stable versions within 4 weeks of project initiation; Implementation - system shall implement with web technologies like HTML/JSP/PHP; Standards - date format must be DD:MM:YYYY.

3.2.3 External Requirements: Security - system shall authorize the user to prevent access from outside of college; Interoperability - system shall operate with college database.

3.3 Interface Specification: Various GUI elements like forms, images and standard buttons will be included in the User Interface.

4. Appendices: Administrator - a login id representing a user with user administration privileges; User - a general login id assigned to most users; Client - intended users for the software; Interface - something used to communicate across different mediums.

Software Design Document (SDD): The Library Management System is divided into two modules - Student and Admin. Admin can add/update/delete members, add/update/delete books, issue new books to students, search students by student ID, view student details, and change own password. Students can register and get a student-id, view their dashboard, view listed books, update their profile, view issued books and return date-time, and change or recover their password.

Test Plan: The test plan covers Librarian Interface (Master Data, User Management, Reports), Student Interface (Profile, Search, Reserve), and Faculty Interface (Profile, Search, Reserve, Request Order). Features to be tested include adding new categories/books, editing categories/books, managing transactions, creating/editing members, generating reports, login, viewing issue details, searching books, and reserving books.

Study and Usage of Design Phase CASE Tools

Computer Aided Software Engineering (CASE) tools are software application programs used to automate SDLC activities. CASE tools are used by software project managers, analysts and engineers to develop software systems. There are a number of CASE tools available to simplify various stages of the Software Development Life Cycle such as Analysis tools, Design tools, Project management tools, Database Management tools, and Documentation tools.

UML Modeling Tools:

  • Rational Rose - IBM Rational Software Architect
  • StarUML
  • EdrawMax
  • Lucid Chart
  • Creately
  • Visual Paradigm
  • Visio
  • Draw.Io
  • Altova
  • Modelio

StarUML: StarUML is a UML tool developed by MKLab. It is a software modeling platform that supports UML (Unified Modeling Language). StarUML supports many UML diagram types. The user can freely create and manage different diagrams as needed. StarUML uses its own file format with the .uml extension. Modeling approaches include 4+1 View Model, Default Approach, Rational Approach, UML Components Approach, and Empty Approach.

Performing the Design by Using Design Phase CASE Tools

The design of the Book Bank - Library Management System was performed using StarUML. Design Structural Models include Class Diagram (static structure with classes like Book, Author, Student, Issue, Fine) and Object Diagram (instances of classes and their relationships). Design Behavioral Models include Use Case Diagram (actors: Student, Librarian, Faculty), Sequence Diagram (object interactions in time sequence), Collaboration Diagram (structural organization of objects), Statechart Diagram (states: Available, Issued, Returned, Overdue), and Activity Diagram (workflow of book issue and return). Design Architectural Models include Component Diagram (Book Management, User Management, Issue Management, Fine Management) and Deployment Diagram (Web Server, Database Server, Client Browsers).
